Read for understanding, run for evidence, and change the example to discover where the abstraction holds.

Pass one: learn the boundaries

  1. Strategy: replace one algorithm without changing its caller.
  2. Adapter: make one existing dependency fit a client-owned contract.
  3. Factory: move construction decisions to one place.
  4. Decorator: trace behavior through two ordered wrappers.
  5. Observer: reason about the lifetime of a subscription.

For each chapter, draw the participants from memory, run the example, and explain the call path aloud. Then remove the pattern and write the simplest equivalent implementation. Comparing both versions teaches you when the abstraction pays for itself.

Pass two: model state and structure

Study State, Command, and Memento together. Build a transition table, trace undo/redo stacks, and identify which state each snapshot owns. Then connect Composite, Iterator, and Visitor: one structures data, one traverses it, and one adds operations over its types.

Pass three: challenge the design

Return to the remaining chapters with a concrete change in mind. Try adding a family to Abstract Factory, a channel to Bridge, a step to Template Method, and a new element to Visitor. Record which files change. The exercise exposes the extension direction each design favors.

Read Singleton and Flyweight after understanding ownership. Their surface code is small, but their important questions concern lifetime, sharing, concurrency, and measurement.

A repeatable practice loop

  1. Read the problem and predict the simplest solution.
  2. Trace one successful call through the actual source.
  3. Find an unsupported input or failure path.
  4. Write the behavior you want as a contract.
  5. Implement the chapter exercise and test that contract.
  6. Compare the same decision in a second language.
  7. Write three sentences explaining the benefit, cost, and simpler alternative.

A design review you can reuse

  • What concrete requirement creates the need for this boundary?
  • Which dependency does the pattern remove, and which one does it add?
  • What is easy to extend? What becomes harder?
  • What happens after a partial failure or concurrent call?
  • Can a reader locate construction, ownership, and cleanup?
  • Which test demonstrates the promised benefit?
  • What evidence would make us remove this abstraction?

Capstone: a document publishing tool

Build a small tool that stores document elements, previews an export, and moves a draft through review and publication. Start with plain data and functions. Introduce a pattern only after you can name the pressure: perhaps Visitor for growing export operations, State for lifecycle rules, and Command for local editing history.

Add one constraint at a time: a new element, a new exporter, rejected review, then concurrent edits. Submit a short decision record explaining why you used each pattern and why you declined others. A strong solution may use fewer patterns than you first expected.
