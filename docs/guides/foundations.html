A pattern earns its place when it makes a real change easier to reason about. Start with the pressure on the design, then choose the smallest useful boundary.

Design around a reason to change

Imagine checkout knows how to format legacy gateway requests, choose a payment provider, retry failed calls, and update an order. Those decisions change for different reasons. A provider migration should not require rewriting order policy. Splitting responsibilities around those reasons gives the code a more stable shape.

Patterns name recurring arrangements of those boundaries. Adapter names a translation boundary; Strategy names an interchangeable algorithm; State names behavior tied to a lifecycle. Their value comes from the dependency they remove and the contract they make explicit.

Before introducing a pattern, finish this sentence: “When ___ changes, I want to avoid changing ___.”

A contract is more than a method signature

Two payment strategies may both expose a pay method while differing in settlement, refunds, and retry safety. If clients assume properties that only one implementation has, the abstraction is misleading. Write down inputs, outputs, failures, ownership, timing, and side effects before claiming implementations are interchangeable.

Substitutability means the client’s valid expectations survive replacement. A caching proxy that returns stale data may need a freshness field. An adapter that rounds amounts may violate the target contract even if every type checks. A decorator that swallows failures changes semantics even if it preserves the interface.

Put composition in one visible place

The application entry point is a good place to choose concrete factories, strategies, and wrappers. Construct the object graph there and pass collaborators into clients. This keeps selection policy visible and makes tests able to substitute small fakes without changing production code.

Dependency injection does not require a container library. Passing a weather service to a proxy or a channel to a notification is enough. A container is useful only when its lifecycle and wiring facilities solve a problem the application actually has.

Use principles as questions

  • Single responsibility: would unrelated changes force edits to this module?
  • Open/closed: which extension should be possible without modifying stable callers? Every design remains closed along some other axis.
  • Substitution: does each implementation preserve the behavior clients rely on?
  • Interface segregation: does this client depend on operations it never needs?
  • Dependency inversion: does business policy depend on its own contract or on a vendor’s details?

These are evaluation tools, not a requirement to create an interface for every class. A private helper with one implementation can remain a private helper.

Refactor from evidence

  1. Describe a concrete change that is currently difficult.
  2. Capture existing observable behavior in tests.
  3. Find the decision that varies and give it a small contract.
  4. Move one implementation behind that contract.
  5. Try a second real implementation to test whether the boundary is honest.
  6. Remove scaffolding that does not make the change easier.

Keep data formats and public behavior stable during structural changes where possible. A refactoring that also changes error policy, persistence, and user behavior is harder to review because structural and semantic changes become entangled.

Use accurate names

The repository’s factory examples are simple factories; the factory chapter also explains canonical Factory Method. A fluent setter chain is not automatically a Builder. A callback is not automatically an Observer system. Calling every coordinating class a Mediator obscures the specific collaboration it owns.

Prefer a domain name such as OrderCheckout or WeatherCache in production code when it communicates intent more clearly than a pattern suffix. Discuss the pattern in design notes; let the API speak the language of its users.
